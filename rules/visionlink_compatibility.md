# VisionLink 호환 규격과 기능 등록

점검일 2026-10-13 · 기준 코드 `cf9d0863` + 작업 트리

## 버전의 의미

- **앱 버전**은 각 앱의 배포 버전이다. 세 앱의 숫자를 맞추지 않는다. 연결 메시지의 `app.id/version/build`는 설치본 확인과 진단에만 사용하며 기능 지원 여부를 추정하지 않는다. 실제 Android PackageInfo/BuildConfig와 iOS Bundle 값에서 읽는다.
- **VisionLink protocol = 1**은 최초 공개 규격이다. 연결 방식이나 기존 메시지 의미가 호환되지 않게 바뀔 때만 올린다. 현재 구현은 규격 1만 수락한다.
- **기능 ID의 `.v1`**은 해당 기능의 메시지 의미·필수 필드 규격이다. 하위 호환 필드 추가는 기존 ID를 유지하고, 의미가 달라지면 새 ID를 추가한다. 버그 수정·색상·문구 변경만으로 규격을 올리지 않는다.
- 앱은 아직 VisionLink 포함 버전을 출시하지 않았다. 아래 앱 버전은 개발 기준이며 출시 완료를 뜻하지 않는다. 출시 직전 최종 버전·빌드와 커밋을 이 표에 확정하고, 배포할 빌드 번호는 이전 배포보다 증가시킨다. 현재 개발본끼리도 앱 버전만으로 이 변경 포함 여부를 판단할 수 없으므로 hello와 기능 목록으로 확인한다.

| 구현 | 최초 지원 개발 기준 | 최초 공개 버전 |
|---|---|---|
| VisionLink 송신 Android/iOS | `1.0.0+1`의 규격 1 구현 작업 트리 | 미출시·릴리스 시 확정 |
| 리보탭 | `1.2.2 (49)`의 규격 1 구현 작업 트리 | 미출시·릴리스 시 확정 |
| 리보패드 | `1.0 (1)`의 규격 1 구현 작업 트리 | 미출시·릴리스 시 확정 |

## 연결 협상

WebRTC `visionlink-file` ordered 데이터 채널이 열린 뒤 송신기가 `visionlink-hello`를 보낸다. 수신기는 같은 `requestId`로 자기 정보를 응답한다. 서버 페어링·시그널링 API는 변경하지 않는다.

```json
{
  "type": "visionlink-hello",
  "requestId": "channel-unique-id",
  "protocol": 1,
  "role": "camera",
  "app": {"id": "net.rivo.visionlink", "version": "1.0.0", "build": "1"},
  "features": ["core.v1", "camera.v1", "camera-zoom.v1", "camera-orientation.v1", "file.v1", "text.v1", "remote-actions.v1", "media-recovery.v1"],
  "video": {"maxHeight": 1080, "maxFps": 30}
}
```

- 수신 응답의 `role`은 `receiver`다. `maxHeight`는 방향과 무관한 영상의 **짧은 변 픽셀 수**, `maxFps`는 상한이다. 현재 세 앱은 1080·30을 광고한다. 카메라 하드웨어의 실제 출력 보장이 아니다.
- 송신기는 즉시 전송하고 응답이 없으면 1초 간격으로 최대 5회 보낸다. 5초 내 확인되지 않으면 사용을 차단한다. 수신기는 채널 open 후 6초 내 유효한 협상을 완료하지 못하면 차단한다. 같은 요청의 재전송은 같은 응답으로 처리한다.
- 공통 기능은 목록의 교집합, 영상 상한은 양쪽 값의 최솟값이다. 송신은 첫 인코더 설정과 이후 자동 화질 조절 모두 이 상한을 지킨다. 첫 인코더 설정이 실패하면 카메라를 정리하고 공유 시작을 실패로 처리하여 미적용 상한으로 전송하지 않는다. 공통 상한이 720p 또는 24fps보다 낮으면 카메라 공유를 시작하지 않는다. 파일·텍스트 등 다른 공통 기능은 유지한다.
- 카메라 캡처·파일·텍스트·원격 요청은 협상이 끝난 뒤 시작한다. 수신기도 협상 전 제어·바이너리와 영상 표시를 차단한다. 모르는 기능 ID·추가 필드는 무시하며 모르는 명령은 실행하지 않는다.
- 프로토콜 불일치, 필수 `core.v1` 누락, 잘못된 형식, 응답 없는 개발본은 “VisionLink 호환 규격을 확인할 수 없습니다. 송신앱과 수신앱을 모두 업데이트한 뒤 다시 연결해주세요.”를 표시한다. 버전 문제를 네트워크 오류로 간주하여 즉시 자동 재연결하지 않는다. 페어링 등록은 보존한다.
- 첫 유효한 협상 결과는 채널이 끝날 때까지 고정한다. 송신 응답은 해당 채널 요청 ID로 확인하며, 이전 채널의 이벤트·타이머는 새 연결에 반영하지 않는다. 재연결은 새로 협상한다.
- 앱 버전 정보가 없거나 표시 문자열이 달라도 호환 판정은 protocol/features/video로만 한다. 프로토콜·치수·fps는 유한한 정수, 기능 목록은 최대 64개·ID당 80자, 요청 ID는 1~80자다. 허용 치수 0~16384·fps 0~240은 파싱 한도이며 실제 지원 상한이 아니다.

## 최초 기능 목록

다음 항목은 모두 **protocol 1 / 위 세 앱의 최초 공개 기준**에 포함한다. `remote-actions.v1`은 현재 함께 제공되는 원격 처리 묶음이며, 이후 독립적으로 추가되는 기능은 별도 ID로 등록한다.

| 기능 ID | 포함 메시지·동작 | 상대 미지원 시 |
|---|---|---|
| `core.v1` | hello, `data-ping/pong` | 연결 사용 차단·양쪽 업데이트 안내 |
| `camera.v1` | `camera-share-state`, 720p/1080p 자동 화질, 720p·24fps 표시 기준 | 카메라 공유 차단·다른 공통 기능 유지 |
| `camera-zoom.v1` | `camera-zoom-state/request`, 실제 배율 동기화 | 원격 확대 명령·상태를 보내지 않음; 폰 자체 확대는 가능 |
| `camera-orientation.v1` | `camera.v1` 필요. 실제 기기 자세를 프레임별 WebRTC 회전 정보로 전송·표시 | 별도 방향 추적을 켜지 않고 기존 WebRTC 방향 처리 유지 |
| `file.v1` | `file-start/accepted/end/cancel/complete/error`와 바이너리 | 파일 전송 전 업데이트 안내 |
| `text.v1` | `clipboard-text/complete/error` | 텍스트 전송 전 업데이트 안내 |
| `remote-actions.v1` | `feature-*`, `chat-*`, `live-reading-*`: OCR·이미지 설명·번역·AI 대화·첨부·실시간 읽기 | 해당 요청 전 업데이트 안내; 이미지/첨부 전송에는 file도 필요, 실시간 읽기에는 camera도 필요 |
| `media-recovery.v1` | `media-recovery-request` | 요청 실패를 반환하고 기존 전체 연결 복구 경로 사용 |

미지원 선택 기능의 홈 진입점은 유지하되 실행 전 안내하고 전송하지 않는다. 수신 확대 조작은 확인된 확대 상태가 없으면 활성화하지 않는다. 공유 HUD는 기존 `1080p · 1.5x`만 유지한다. 송신·리보탭 진단 로그의 `COMPAT`에서 규격·상대 앱 버전·공통 기능을 확인할 수 있다(송신 로그에는 영상 상한도 포함).

**4K는 구현하지 않았다.** 미래 송신기가 2160p를 광고해도 현재 수신기는 1080p 상한을 반환하므로 공통 상한은 FHD다. 이 시나리오는 협상 단위 테스트에만 들어 있다.

## 카메라 방향과 화면 방향

`camera-orientation.v1`은 protocol 1의 선택 기능이다. 최초 지원 개발 기준은 송신 `1.0.0+1`, 리보탭 `1.2.2 (49)`, 리보패드 `1.0 (1)`의 현재 작업 트리이며 모두 미출시다. 양쪽이 지원할 때 송신기의 물리 방향 추적을 활성화한다. 새 JSON 방향 메시지 없이 WebRTC의 프레임별 회전 메타데이터(CVO)를 사용하며 수신 렌더러는 이를 한 번만 적용한다. 수신 UI 자체의 방향은 바꾸지 않는다.

송신 홈·설정은 Android/iOS 모두 세로이며 공유 화면에서만 가로 회전을 허용한다. 영상·제목·HUD·버튼은 공유 화면과 함께 돌아가며 중지 버튼은 가로에서 오른쪽 아래 내용 폭(최대 320dp), 세로에서 기존 폭을 사용한다. 공유 중지·연결 종료·화면 종료 시 세로로 복귀한다. Android는 화면 회전 대신 OrientationEventListener와 카메라 센서 방향·전후면을 조합하고, 경계 흔들림에는 15도 여유를 둔다. 평평하거나 방향을 판단할 수 없으면 마지막 유효 방향을 유지하며 처음에는 원래 프레임 방향을 사용한다. iOS는 RTCCameraVideoCapturer의 UIDevice 방향 처리를 사용한다. 카메라 중지·종료 때 추적을 해제한다. 송신 공유 미리보기는 비율을 유지하며 화면을 꽉 채운다(cover). 양쪽 수신기는 전체 프레임을 비율 유지로 맞춘다. 송신 폰의 방향 때문에 수신 UI를 강제 회전시키지 않는다. 이 표시 수정은 기존 camera-orientation.v1의 UI 동작이며 protocol·기능 ID를 올리지 않는다.

검사: 세 앱의 기능 교집합·기능 누락 fallback, Android 전후면 4방향·경계 흔들림·알 수 없는 자세, 리보패드 읽기 프레임의 4방향 치수를 확인한다. 공유 화면의 가로 회전·오른쪽 아래 중지 버튼·중지 후 세로 복귀와 가로 영상 수신은 별도 실기기 확인 대상으로 기록한다.

## 기능 변경 시 필수 절차

1. 이 문서와 양쪽 `rules/visionlink.md`를 먼저 읽고 송신·리보탭·리보패드의 대응 코드를 확인한다.
2. 기능 ID·요구 protocol·최초 지원 앱 버전/빌드·필수 의존 기능·미지원 시 동작을 먼저 정한다. 출시 번호가 미정이면 미출시로 적고 출시 때 확정한다.
3. 실행 전 공통 지원 여부를 검사하고, 미지원 명령을 전송하지 않는다. 수신기도 미협상 명령을 실행하지 않는다. 영상 제한은 최초 설정·자동 상향·재연결 모두 적용한다.
4. 세 앱의 기능 목록과 이 문서 사본을 함께 갱신한다. 한쪽이 구현되지 않았으면 그쪽 기능 목록에 넣지 않는다. 배포 버전만 같게 올려서 지원을 가장하지 않는다.
5. 신↔신, 신송신↔구수신, 구송신↔신수신, 선택 기능 누락, 불명 기능, 필수 규격 불일치, hello 유실·시간 초과, 재연결·지연 메시지를 확인한다. 새로운 수치 상한은 작은 쪽 선택도 확인한다.
6. 각 플랫폼의 빌드·테스트와 실제 수행한 기기 검증을 기록한다. 빌드 성공과 실기기 동작을 구분한다. M5는 사용자 지시로 빌드·설치·테스트 대상에서 제외한다.
