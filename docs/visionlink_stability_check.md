# VisionLink 안정성 점검 — 2026-10-12

## 적용 범위와 기준

Flutter 송신앱(Android·iOS), 리보탭(Android), 리보패드(iPadOS)의 기존 1:1 WebRTC 연결에 적용했다.

- [LiveKit 연결 복구](https://docs.livekit.io/intro/basics/connect/): 경로 재협상 후 실패 시 전체 재연결과 트랙 재게시라는 단계적 복구 원칙을 적용했다.
- [Google WebRTC 영상 적응](https://webrtc.googlesource.com/src/+/HEAD/video/g3doc/adaptation.md): 해상도·fps 중복 축소를 막고 네트워크 혼잡 제어와 인코더 부하를 함께 관찰한다.
- [Twilio 네트워크 품질](https://www.twilio.com/docs/video/using-network-quality-api): 품질은 현재 스트림 요구량과 지연·손실에 상대적이며, 실제 미디어 전송률을 인터넷 전체 속도로 해석하지 않는다.

## 반영한 동작

실제 프레임이 5초간 없으면 ICE 재시작을 한 번 요청하고, 12초 더 프레임이 없으면 전체 연결을 복구한다. offer 대기는 8초, 송신 answer 대기는 12초다. WebSocket·데이터 채널의 응답 대기도 제한한다. 긴 단절에서도 송신 재시도는 계속되며 공유하던 카메라는 전면 복귀 후 재개한다. 수동 공유 중지·등록 해제·종료는 자동 재개하지 않는다.

PC·소켓·데이터 채널의 이전 세대 콜백을 버린다. 연결 종료 후 늦게 열린 카메라를 즉시 해제한다. Android 파일 IO 중 연결이 바뀌면 이전 처리의 화면 알림과 응답을 새 채널에 보내지 않는다.

첫 영상부터 최대 1080p·30fps·5Mbps 상한으로 시작한다. 시작 비트레이트 힌트는 3Mbps이고 실제 비트레이트는 WebRTC가 제어한다. 초기 정상 출력은 2초간 안정화한 뒤, 연결 상태나 인코더 부하가 지속되면 상한을 낮춘다. 첫 상한 변경 적용 뒤에는 기존의 신중한 복구 기준으로 돌아간다. 인코더가 제한 없음을 보고하는 정적인 장면은 낮은 추정값만으로 해상도를 낮추지 않는다. 상향·하향의 확인 횟수와 안정화 기간을 두어 순간 추정값에 흔들리지 않게 한다. 표시값은 실제 송신·디코딩 크기와 fps, 미디어 비트레이트다.

- Android 송신 Galaxy A26 → 리보탭 Galaxy Tab S9: 실제 송수신 1920×1080·30fps·약 4.9Mbps 확인. 어두운 입력의 8~9fps는 밝은 곳을 향하게 하자 30fps로 회복됐다.
- 인터넷 20초 단절과 최종 송신앱의 65초 단절을 재현했다. Wi-Fi·모바일 데이터 설정을 원래 값으로 복원했다. 65초 단절은 최초 6회 재시도를 모두 소진한 뒤 다음 재시도까지 이어졌고, 네트워크 복원 약 13초 후 카메라 공유가 자동 재개됐다.
- Android 송신 화면을 10초 끈 뒤 전면 복귀했을 때 약 4.5초 후 카메라 공유가 재개됐다. 수동 공유 중지 후 수신앱을 다시 실행했을 때에는 공유를 자동 재개하지 않았다.
- iPhone 12 mini → 리보패드 iPad M4: 실제 수신 1920×1080·30fps·약 5Mbps 확인. 최종 송신앱으로 홈 화면 이동·복귀 후 영상 재개 확인. 첫 연속 관찰은 다른 HWP 테스트의 앱 재실행으로 중단되어 별도로 다시 검증했다. 빠른 초기 화질 변경 전 안정성 재검증은 8분 30초 동안 15초 간격으로 34회 관찰했으며, 최초 연결 대기를 지나 360p부터 1080p까지 올라간 뒤 30fps·약 4.8~5Mbps를 유지했다. 연속 수신 테스트가 통과했다.
- Galaxy Tab S9의 무선 디버깅을 켜고 USB 없이 명령 실행이 가능한 것을 확인했다. 테스트가 끝난 iPad의 원래 등록 정보를 복원하고 임시 등록·테스트 코드를 정리했다.

## 첫 영상 고화질 검증

최종 송신앱은 720p를 거쳐 올리지 않고 1080p 상한을 첫 인코딩에 적용한다. Android·iOS 송신앱 모두 최종 빌드·설치를 완료했다. 회선 추정값이 없어도 초기 상한은 1080p이고, 출력·CPU·손실·지연·혼잡을 보고 낮춘다. 정적인 영상의 낮은 추정값, 실제 혼잡, CPU 과부하, 재시작, 하향 후 복구 기준을 테스트에 포함했다.

- Galaxy A26 → Galaxy Tab S9: 첫 측정부터 1920×1080·30fps. 공유 직후 수 초간 3.5→4.9Mbps로 전송량이 안정화됐다. 첫 영상에 360p·720p 단계가 없었다. 현재 전체 Kotlin 작업 트리로 빌드한 수신앱 설치 후에도 태블릿 화면의 실제 화질 표시가 1920×1080·30fps·5.0Mbps임을 확인했다.
- iPhone 12 mini → iPad M4: 공유 시작 5초 뒤의 첫 수치 측정이 1920×1080·29fps였고 다음 측정부터 30fps였다. 30초간 관찰 중 1080p·30fps를 유지했다. 수치는 두 번의 통계를 비교하므로 초기 수치 측정 대기는 영상 해상도 상향 대기가 아니다.
- 실제 화면과 상태를 읽는 양쪽 iOS UI 테스트 통과. iPad 원래 등록 정보 복원 및 임시 등록 삭제 완료.

Android 초기 검증은 문서 엔진 API·원격 참조 커밋 문제를 피하기 위해 `2b8a29a`의 별도 작업 트리에 최종 비전링크 파일 28개를 복사해 수행했다. 이후 현재 Kotlin 작업 트리도 13개 테스트·APK 빌드를 통과했다. 이 마지막 빌드는 `engine-bridge/Package.swift`와 모든 `Sources`가 일치하는, 별도 문서 작업에서 이미 빌드·검증한 Swift 엔진 산출물을 재사용했다(`-x :app:buildSwiftDocumentEngine`). 엔진을 누락하는 빌드 옵션은 사용하지 않았다. 원격 참조를 가져오는 기본 Swift 빌드 경로는 별도 확인이 필요하다.

## 최소 품질 표시 기준 검증

송신 상한은 720p·1080p 두 단계로 제한했다. 양쪽 수신 앱의 `VisionLinkVideoDisplayGate`는 실제 영상의 짧은 변 720픽셀 미만 또는 24 decoded fps 미만(측정 불가·정지 포함)이 8초 지속되면 불투명 안내로 가린다. 두 기준을 4초 연속 만족하면 다시 표시한다. 낮은 비트레이트만으로는 가리지 않으며 디코딩·통계·연결 복구는 계속된다. 안내는 네트워크만 원인으로 단정하지 않는다.

- Flutter 전체 49개 테스트·analyze 통과, Android APK·iOS Release 빌드 성공. CPU·혼잡에 따른 1080→720 하향과 720 하한 유지, 720→1080 복귀를 확인했다.
- 리보탭 18개 테스트·빌드 통과, 리보패드 화질 관련 9개 테스트를 iPad M4에서 통과했다. 8초 차단·4초 회복 경계, 세로 720p·정확히 24fps 허용, 1080p 저fps 차단, 순간 저하·회복 중 다시 저하, 통계 공백·초기화가 포함된다.
- 실기기에서만 사용한 별도 송신 빌드로 첫 50초 인코딩을 12fps로 제한한 뒤 같은 연결에서 30fps로 복구했다. Galaxy A26→Galaxy Tab S9와 iPhone 12 mini→iPad M4 모두 1080p·12fps가 지속될 때 안내·영상 가림을 확인했다. 1080p·30fps로 돌아오자 안내가 사라지고 실제 영상이 자동 복귀했다. Android 안내 화면도 캡처로 불투명 가림·문구·실제 화질 표시를 확인했다.
- iPad UI 자동화 테스트와 iPhone 공유 테스트 통과. 최종 설치본에는 테스트용 프레임 제한이 없으며, 송신 소스도 테스트 전에 저장한 원본으로 복원한 뒤 정식 Android·iOS 빌드를 다시 만들었다. 임시 iPad 등록 삭제와 원래 정보 복원 테스트도 통과했고 테스트 소스를 제거했다.


최소 품질 변경의 리보탭 검증본은 16:17에 빌드·18개 테스트를 통과한 APK다. 두 태블릿의 최소 품질 실기기 검증은 통과했으나, 이후 다른 작업의 태블릿 테스트가 서로 다른 APK를 반복 설치하는 것이 설치 시각·해시 차이로 확인됐다. 사용자가 다른 테스트를 멈춘 뒤 2026-10-12 17:27 KST에 리보탭 검증본 재설치를 완료했다. 설치된 APK 해시가 검증본과 일치하며, 송신 Galaxy A26과 리보탭 화면에서 실제 1920×1080·30fps·약 4.6~4.8Mbps를 확인했다. 최소 품질 표시 기능의 최종 설치 대기는 해소됐다. 검증본은 `/tmp/visionlink-min-quality-rivotab-validated.apk`로 보존했다(sha256 `53df7cd48b38c7edde88f2a387133fe1bf690adecbb17725aef6cb38a482e9c2`). 이후 같은 작업 트리에서 별도로 진행 중인 엑셀 화면·문서 엔진 수정 때문에 전체 재빌드가 컴파일 오류를 냈다. 해당 변경은 보존하고, 비전링크 소스는 이미 검증·설치된 빌드와 일치하도록 유지했다. 진행 중인 엑셀·새 엔진 변경까지 포함한 전체 앱 검증은 이번 결과에 포함하지 않는다.

## 검증의 범위

현재 연결된 기기와 실제 Wi-Fi 연결에서 확인했다. 이동통신 단독 경로, 먼 거리·다른 통신사 NAT, TURN/TLS 강제 경로, 수 시간 이상의 발열·배터리 검증은 이번에 재현하지 않았다. TURN 주소나 자격 증명을 임의로 추가하지 않았으며 서버 배포는 변경하지 않았다. 1080p는 최대 상한이고 카메라 입력·인코더·회선 상황에 따라 낮아질 수 있다.
