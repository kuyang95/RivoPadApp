# Word AI 장문 문서 검색·편집 설계

상태: 1차 기반 구현 완료
기준일: 2026-08-25

## 목표

사용자가 문단을 미리 선택하지 않아도 긴 DOCX에 자연어로 질문하거나 수정할 수
있어야 한다. 매 요청마다 문서 앞부분부터 최대 80,000자를 보내는 대신, 질문을
받은 뒤 관련 구역을 찾고 그 본문만 최종 Word AI 호출에 보낸다.

이 설계의 우선 목표는 다음 세 가지다.

1. 장문 문서의 입력 토큰을 줄인다.
2. 문서 뒤쪽에 있는 내용도 찾는다.
3. 편집 대상이 여러 개면 추측하지 않고 기존 `clarify` 경로로 되묻는다.

## 현재 문제

`WordAISnapshotBuilder.make`는 `userRequest`를 받지 않는다. 선택 문단이 없으면
문서 순서대로, 선택 문단이 있으면 선택 주변을 먼저 넣은 뒤 계속 문단을 추가해
최대 600블록·80,000자를 채운다. 따라서 질문과 무관한 앞부분이 전송되고 뒤쪽
근거는 잘릴 수 있다.

`contextWasTruncated`만으로는 이 문제를 해결할 수 없다. 모델은 전송되지 않은
문단에 다른 날짜나 같은 이름의 항목이 있는지 알 수 없기 때문이다.

## 요청 처리 흐름

```text
사용자 질문
  → 로컬에서 문서 구역 카탈로그와 정확 검색 후보 생성
  → 작은 문서는 기존 단일 호출
  → 큰 문서는 Gemini 라우팅 호출
       ├─ 모호함: clarify 문구를 사용자에게 표시하고 종료
       └─ 구역 선택: sectionIDs/blockIDs 반환
  → 선택 구역과 후보 주변만 Word 스냅샷으로 구성
  → 기존 Word AI answer/clarify/edit 호출
  → 기존 로컬 검증과 수정안 미리보기
```

라우팅 호출은 답을 작성하거나 문서를 수정하지 않는다. 어떤 구역이 필요한지만
고른다. 문서 데이터는 라우팅 단계에서도 신뢰하지 않는 입력으로 취급한다.

## 로컬 카탈로그

DOCX에서 이미 추출한 `WordDocumentBlock`을 재사용한다.

- `title`, `heading1`, `heading2`, `heading3`로 제목 경로를 만든다.
- 한 구역이 지나치게 크면 블록 수와 문자 수 기준으로 하위 조각을 만든다.
- 각 구역은 `sectionID`, 제목 경로, 블록 범위, 짧은 첫 내용만 가진다.
- 질문의 정확 문자열·숫자·날짜와 겹치는 문단은 별도 후보로 넣는다.
- 표 셀 후보에는 기존 `tableLocation` 설명을 함께 넣는다.
- 카탈로그 크기는 별도 상한을 두고, 잘렸다는 사실을 라우터에 전달한다.

1차 상한은 구역 100개·정확 후보 20개다. 구역 미리보기는 180자, 후보
미리보기는 320자로 제한한다. 최종 본문 스냅샷은 160블록·24,000자까지 담는다.
이 상한은 라우팅 호출과 최종 호출의 합이 기존 80,000자보다 커지는 것을 막기
위한 초기 안전값이다.

로컬 점수는 최종 의미 판단이 아니다. 라우터가 볼 후보를 보강하기 위한 값이다.
동의어·모호성의 최종 판단은 Gemini가 수행한다.

## 라우팅 응답

최종 편집 명령인 `WordAICommandPlan`과 분리된 작은 스키마를 사용한다.

```json
{
  "intent": "retrieve",
  "assistantMessage": "관련 구역을 찾았습니다.",
  "sectionIDs": ["word-section-word-paragraph-120"],
  "blockIDs": ["word-paragraph-128"]
}
```

모호하거나 카탈로그만으로 위치를 찾을 수 없으면 다음처럼 반환한다.

```json
{
  "intent": "clarify",
  "assistantMessage": "표지의 작성일과 변경 이력의 작성일 중 어느 것을 변경할까요?",
  "sectionIDs": [],
  "blockIDs": []
}
```

앱은 반환된 ID가 실제 카탈로그에 있는지 검증한다. `retrieve`인데 유효한 ID가
하나도 없거나, `clarify`인데 ID가 포함되면 응답을 거부한다.

## 최종 스냅샷

라우터가 고른 구역 본문, 직접 고른 블록의 앞뒤 문단, 필요한 제목 블록을 문서
순서로 담는다. 각 블록은 기존 ID와 편집 가능 여부를 그대로 유지한다.

문서 전체 revision은 선택된 일부 블록이 아니라 전체 블록으로 계산한다. 따라서
AI 수정안 생성 중 전송되지 않은 문단이 바뀌어도 기존 stale proposal 검사가
수정 적용을 막는다.

최종 Word AI 프롬프트에는 다음 사실을 명시한다.

- 입력 블록은 전체 문서가 아니라 질문으로 검색한 결과다.
- 필요한 근거가 없으면 추측하지 말고 `clarify`한다.
- 같은 레이블·날짜·숫자의 편집 후보가 여러 개면 `edit`하지 않는다.
- 편집은 입력에 포함된 정확한 `blockID`에만 제안한다.

## 작은 문서와 폴백

작은 문서는 라우팅 호출이 오히려 비용과 지연을 늘리므로 기존 단일 호출을 쓴다.
초기 기준은 전체 160블록 이하이면서 24,000자 이하이다. 이 값은 실제 토큰과 사용
통계로 조정한다.

큰 문서에서 카탈로그가 잘렸고 관련 구역을 찾지 못하면 문서 앞 80,000자로
조용히 폴백하지 않는다. 잘못된 근거로 답하는 대신 사용자에게 고유 문구·제목·
날짜 중 하나를 묻는다.

## 선택 문단 focused 경로

이번 구현 범위에서 제외한다. iPad·VoiceOver 사용자가 문단을 먼저 선택한다고
가정하지 않는다. 나중에 선택 상태가 명시적인 단축 경로로 제공될 수 있지만,
비선택 검색·편집이 기본 동작이다.

## 전체 요약

전체 요약은 검색 문제가 아니다. 모든 내용을 읽어야 하므로 장별 분할 요약과
revision 기반 요약 캐시로 처리한다. 이번 라우팅 구현에 포함하지 않는다.

## 임베딩

한국어 다국어 임베딩 모델 번들은 앱 크기·메모리·인덱싱 비용을 측정한 뒤 검토한다.
개요 라우팅과 정확 검색 후보만으로 부족하다는 평가 결과가 있을 때만 추가한다.

## 구현 위치

- `WordAIRetrieval.swift`: 카탈로그, 라우팅 계획, 검색 스냅샷 빌더
- `WordAICommandService.swift`: Gemini 라우팅 호출과 응답 검증
- `WordAIChatView.swift`: 질문을 카탈로그·스냅샷 제공자에 전달하는 오케스트레이션
- `WordDocumentView.swift`: 현재 블록에서 카탈로그와 최종 스냅샷 생성
- `WordDocumentEditingTests.swift`: 구역 생성, 뒤쪽 후보 검색, 라우팅 응답 검증,
  검색 스냅샷 범위와 revision 회귀 테스트

## 1차 구현 완료 범위

- 질문을 받은 뒤 로컬 카탈로그 생성
- 작은 문서 단일 호출과 큰 문서 2단계 호출 분기
- 제목 경로·구역 조각·정확 문구/숫자/날짜 후보 생성
- Gemini 라우팅 응답 스키마와 실제 ID 검증
- 라우팅 `clarify`를 기존 채팅 응답으로 연결
- 선택 구역·직접 후보·앞뒤 문단만 최종 스냅샷에 포함
- 전체 문서 revision을 유지한 stale proposal 검사
- 문서 끝 후보 검색, 작은 문서 폴백, 임의 ID 거부 단위 테스트

엄격 자동 기준 12/16, 수동 판독 기준 14/16이었으며 측정 토큰의 91.7%를 1차
라우터가 사용했다. 자세한 실패와 한계는 `WORD_AI_LIVE_EVAL_REPORT.md`를 따른다.

검색 뒤 생성된 답을 앱이 어디까지 검증할 수 있는지는 2026-08-26에 별도 POC로
평가했다. 정확 원문 추출형 사실에는 가능성이 있었지만 부정문 잘라내기와 되묻기
메시지 우회가 재현됐으므로 아직 제품에는 연결하지 않았다. 계약, 실제 Gemini
10문항 결과와 적용 전 조건은 `WORD_AI_GROUNDING_POC_REPORT.md`를 따른다. 두 직접
우회를 막은 2차 평가에서도 10/10 기대 동작을 확인했지만 앞 문장 조건 누락과
잘못된 시나리오 선택이 남았다. 최신 결과는
`WORD_AI_GROUNDING_POC_V2_REPORT.md`를 따른다. 후속 3차 비교에서는 3문장 표시가
앞 문장 조건을 보존했지만, 최상위 후보 ID 절대 게이트가 동의어 정상 답변도
거절했다. 비교 수치와 제품 판단은 `WORD_AI_GROUNDING_POC_V3_REPORT.md`를 따른다.

4차 POC에서는 `localAmbiguityDetected`를 빈 차단이 아니라 로컬 원문 후보를 보여주는
`clarify`로 바꿨다. 고령자 인구 비율 20.3%와 고용 비율 38.2%가 실제 Gemini
평가에서도 함께 표시됐다. 차단 사유 매핑과 UI 적용 조건은
`WORD_AI_GROUNDING_POC_V4_REPORT.md`를 따른다.
