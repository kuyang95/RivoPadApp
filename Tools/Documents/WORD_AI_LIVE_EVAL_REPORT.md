# Word AI 장문 검색 라이브 평가 보고서

- 실행일: 2026-08-25
- 장치: 11-inch iPad Pro (M5), iPadOS 26.6
- 모델: Firebase AI Logic `gemini-2.5-flash-lite`
- 평가 대상: `WordAIRetrievalCatalogBuilder` → `WordAICommandService.route` → `WordAISnapshotBuilder.makeRetrieved` → `WordAICommandService.plan`
- 상태: 결과만 기록했으며, 발견한 제품 로직의 허점은 이 평가 중 수정하지 않았다.

## 결론

현재 2단계 검색은 **관련 본문을 아주 작게 줄이는 데는 성공**했지만, **1차 라우터 카탈로그 비용과 응답 안정성은 아직 출시 기준에 못 미친다.**

- 엄격한 자동 평가: **12/16 (75.0%)**
- 수동 판독상 사실적으로 맞거나 안전하게 유용한 결과: **14/16 (87.5%)**
- 유효한 라우팅 응답: **14/16 (87.5%)**
- 유효한 라우팅 14건의 근거 포함률: **14/14 (100%)**
- `작성일: 2026-08-25`를 하루 뒤로 바꾸는 편집: **성공**
- 측정된 토큰: **최소 252,080토큰**
  - 라우터: 231,117토큰, 측정량의 **91.7%**
  - 최종 명령 모델: 20,963토큰, 측정량의 **8.3%**
  - 실패한 라우팅 2건은 현재 하네스가 실패 후 차이를 기록하지 못해 총량에서 빠졌다. 실제 사용량은 252,080보다 크다.

따라서 “관련 문단만 보내면 회당 3천~6천 토큰”이라는 기대는 현재 구현에서는 성립하지 않았다. 유효 응답 기준 평균은 라우터 16,508토큰, 최종 명령 1,497토큰으로 합계 약 18,006토큰이었다.

## 평가 방법

실제 웹 출처로 만든 기존 POC의 질문군을 유지하면서, 라이브 테스트에서는 결과를 결정적으로 판정할 수 있도록 다음 4개 장문 블록 fixture를 만들었다.

| 문서 | 블록 | 문자 | 구역 | 포함한 핵심 주제 |
|---|---:|---:|---:|---|
| 근로기준법 해설 | 253 | 17,141 | 85 | 적용 범위, 해고 예고, 지연이자, 폭행 벌칙, 연차 |
| 2025 고령자 통계 | 253 | 17,983 | 85 | 고령인구, 성별, 인터넷, 메신저, 복수 비율 |
| 2026 경제전망 | 253 | 18,723 | 85 | 성장률, 물가, 경상수지, 수출, 비관 시나리오 |
| 프로젝트 상태 보고서 | 217 | 15,368 | 73 | 문서 뒤쪽의 단일 작성일 |

각 문서는 160블록 기준을 넘기므로 모두 2단계 검색을 사용했다. 질문마다 다음을 기록했다.

1. 1차 라우터의 intent와 선택 section/block ID
2. 최종 스냅샷의 블록 수와 문자 수
3. 스냅샷에 정답 근거가 실제 포함됐는지
4. 최종 answer/clarify/edit 결과
5. 공유 일일 예산의 요청 전후 차이로 계산한 실제 사용 토큰

테스트 본체는 [`WordAIRetrievalLiveTests.swift`](../../shortcuts_exampleTests/WordAIRetrievalLiveTests.swift)에 있으며, 평상시에는 스킵되고 명시적인 컴파일 플래그를 준 장치 테스트에서만 Gemini를 호출한다.

## 토큰과 검색 범위

유효하게 2단계를 모두 마친 14건의 평균은 다음과 같다.

| 항목 | 평균 |
|---|---:|
| 1차 라우터 토큰 | 16,508 |
| 2차 명령 토큰 | 1,497 |
| 합계 | 18,006 |
| 최종 스냅샷 블록 | 10.8개 |
| 최종 스냅샷 문자 | 469자 |

최종 본문은 평균 469자까지 잘 줄었다. 문제는 1차 라우터가 73~85개 구역의 제목, 미리보기, ID와 후보 메타데이터를 모두 받으면서 전체 측정 토큰의 91.7%를 쓴다는 점이다.

이번 fixture는 1.5만~1.9만 자인데도 라우터만 1.38만~1.82만 토큰을 썼다. 이 규모에서는 “전체 본문 1회 호출”보다 2단계가 반드시 싸다고 말할 수 없다. 8만 자 문서에서는 전체 본문보다 유리할 가능성이 있지만, 현재 카탈로그 상한과 형식으로도 회당 1만 중후반 토큰이 들 수 있다는 실제 수치가 확인됐다.

## 발견한 허점

### 1. 라우터의 구조화 응답 안정성

16건 중 2건이 `invalidResponse`로 끝났다. 하나는 명확한 폭행 벌칙 질문이고, 하나는 `clarify`가 필요한 모호한 질문이었다. 두 경우 모두 사용자가 보게 되는 결과는 기존의 “AI 응답을 안전한 Word 수정안으로 바꾸지 못했습니다” 계열 오류다.

현재 서비스는 실패 시 원시 응답이나 정확한 검증 단계(디코딩, 존재하지 않는 ID, ID 개수 초과, 빈 메시지 등)를 평가 로그에 남기지 않는다. 따라서 이번 기록만으로 두 실패가 동일 원인인지 구분할 수 없다.

### 2. 모호성 정책의 일관성

E05는 같은 2.0% 값을 가진 GDP와 물가를 모두 찾아 사실대로 설명했다. 안전하지 않은 추측은 아니지만, 현재 명세의 “여러 의미면 한 가지 질문으로 되묻기”와는 다르다. `clarify`를 강제할지, 여러 후보를 나열하는 안전한 답도 허용할지 제품 정책을 먼저 정해야 평가 기준이 안정된다.

### 3. 카탈로그가 토큰 절감의 병목

검색된 본문은 작지만 카탈로그가 너무 크다. 특히 구역이 100개 이하이면 모든 구역 미리보기를 보내므로, 짧은 문단과 헤딩이 많은 Word 문서에서 메타데이터가 본문과 비슷한 크기가 된다. 현재 방식은 본문 토큰을 카탈로그 토큰으로 옮긴 성격이 강하다.

### 4. 평가기 오탐

L02의 답은 정확했지만 자동 평가가 `5명`이라는 문자열까지 요구해 실패 처리했다. 단순 문자열 검사는 제품 회귀를 빠르게 찾는 데는 유용하지만, 동치 표현을 모두 판정하지 못한다. 이 결과는 제품 실패 통계와 분리해야 한다.

### 5. 실패 요청의 토큰 계측 누락

테스트 하네스는 `route`가 정상 반환된 뒤에만 예산 차이를 저장한다. 구조화 응답 검증에서 실패하면 이미 Gemini가 사용한 토큰이 일일 예산에 반영돼도 결과 행에는 0으로 남는다. 따라서 보고된 252,080은 하한이다.

### 6. XCTest의 App Check 경고

서명된 M5 iPad의 XCTest 호스트에서 App Attest 교환이 반복적으로 HTTP 403을 반환했다. Firebase AI 호출은 완료됐지만 각 요청마다 경고와 재시도가 발생했다. 이는 테스트 지연과 로그 잡음을 만들며, 실제 배포 앱의 App Check 동작과 동일하다고 간주하면 안 된다.

## 이번 평가가 증명하지 않은 것

- 실제 DOCX 파일을 가져와 파싱하는 전 구간 성능은 이번 라이브 평가 범위가 아니다. DOCX 파싱과 저장은 별도 단위 테스트가 통과했다.
- 8만 자 문서, 100개 초과 구역, `catalogWasTruncated=true` 상태는 아직 라이브 평가하지 않았다.
- 동일 질문 반복 시 모델 변동성은 측정하지 않았다.
- 캐시, map-reduce 전체 요약, 온디바이스 임베딩은 구현하거나 평가하지 않았다.

## 다음 판단 지점

로직을 바로 고치기 전에 다음 세 가지를 순서대로 결정하는 편이 좋다.

1. `clarify`만 정답인지, 여러 후보를 명시해 답하는 것도 안전한 성공인지 정책을 확정한다.
2. 1차 카탈로그 목표 예산을 정한다. 현재 관측 평균 16.5k를 허용할지, 예를 들어 4k~6k로 강제할지 결정한다.
3. `invalidResponse`의 원인을 구분할 수 있는 진단을 먼저 추가한 뒤 같은 16문항을 반복한다. 원인을 모른 채 프롬프트나 검색 점수부터 바꾸면 실패가 가려질 수 있다.
