## 결론

친구가 제안한 방향 중 안전한 세 가지를 구현했다.

1. 모델의 자연어 `claim.text`를 사실로 신뢰하지 않고, 검증된 원문 문장을 앱이 표시한다.
2. 검색 1위만 정답으로 취급하지 않고, 로컬 검색 후보 안의 근거를 독립적으로 검증한다.
3. 질문의 연도는 로컬 파서가 만든 신뢰 가능한 제목·범위에서만 상속한다.

동일 사실 병합도 넣었지만, **값이 모두 일치하고 어휘가 강하게 겹칠 때만** 모호성을 해제하도록 보수적으로 구현했다. 값·연도·단위가 다르거나 동등성을 증명하지 못하면 계속 되묻는다.

최종 30문항 결과는 다음과 같다.

- 자동 기대 정책 통과: **16/30**
- 사실 질문을 실제 답변으로 검증: **9/23 (39.1%)**
- 답하면 안 되는 질문 차단: **7/7**
- 안전하지 않은 오답 통과: **0개**
- 상태: `verified` 9, `clarify` 17, `rejected` 4
- 호출 오류: 0
- 사용 토큰: 129,082(문항당 평균 약 4,303)

즉 안전성 게이트는 통과했지만, 정상 사실 질문 14개를 아직 과차단하므로 **그대로 제품에 연결할 수준은 아니다**.

## 구현한 검증 규칙

- 인용의 `blockID`와 문자열이 로컬 원문에 정확히 존재해야 한다.
- 인용 블록은 로컬 검색이 반환한 적격 후보 안에 있어야 한다.
- 모델 답문과 모델 claim은 사실 표시용으로 사용하지 않는다. 앱이 인용이 속한 완전한 원문 문장을 조립한다.
- 질문의 날짜·수치·단위는 원문과 맞아야 한다.
- 구조 범위에서 상속할 수 있는 값은 연·월·일뿐이다. 비율이나 인원 같은 답 수치는 상속하지 않는다.
- 인용문 앞에 다른 연도가 명시되면 제목의 연도로 덮어쓰지 않는다.
- 모호성 병합은 선택된 원문의 모든 수치·단위가 다른 동률 후보에도 존재하고 질문·답 어휘가 충분히 겹칠 때만 허용한다.
- 같은 수치라도 지표·연도·단위가 다르면 되묻는다.
- 검증 실패 이유는 `quoteNotFoundInBlock`, `evidenceNotRelevantToQuestion`, `localAmbiguityDetected` 등으로 사용자 메시지와 내부 진단에 남긴다.

## 구현 중 발견하고 막은 안전 회귀

첫 라이브 수정본은 W09에서 모델이 30.1일/24.5일이 있는 페이지만 인용하자 이를 `verified`로 통과시켰다. 다른 검색 후보에는 31.1일/24.4일이 있었지만, 검증기가 모델이 고른 인용만 비교했기 때문이다.

이를 다음처럼 수정했다.

- 모델 인용은 답 조립에만 사용한다.
- 충돌 검사는 모델이 인용하지 않은 동률 검색 후보도 반드시 검사한다.
- 첫 번째 숫자 하나가 아니라 선택 원문의 모든 수치·단위를 비교한다.
- “9월” 같은 앞쪽 맥락 숫자로 핵심 답 수치 비교를 우회하지 못하게 했다.

재현 테스트 두 개를 추가했고, 최종 라이브 실행에서 W09는 `localAmbiguityDetected`로 차단됐다.

## 남은 허점

정상 사실 질문 14개의 과차단 원인은 세 종류다.

| 원인 | 문항 | 개수 |
|---|---|---:|
| 중복 페이지의 동등성을 보수적으로 증명하지 못함 | P07, S01~S04, S06~S07, W01~W03 | 10 |
| 질문 관련성 임계값 미달 | P02, P05, P08 | 3 |
| PDF 추출 특수문자와 모델 인용의 정확 문자열 불일치 | W08 | 1 |

다음 단계에서는 안전 규칙을 느슨하게 하기보다 다음 두 방법을 별도 POC로 평가하는 편이 낫다.

1. 정확 인용 불일치는 공백·호환문자만 정규화한 뒤 원문 위치를 다시 찾되, 숫자·단위는 완전 일치를 유지한다.
2. 중복 근거는 페이지 전체 숫자가 아니라 질문 지표 주변의 구조화된 값 벡터를 로컬에서 추출해 비교한다.

관련성 임계값을 단순히 낮추는 것은 다른 시나리오의 참인 문장을 오답 근거로 통과시킬 수 있으므로 권하지 않는다.
